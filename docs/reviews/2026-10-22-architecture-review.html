1 · Give the transition table its axes as parameters

Strong in-process
The level axis (beginner / intermediate / advanced) exists only inside state names, so every consumer re-derives it — and 18 rows plus 18 scenario modules are the same module written three times.

Problem. 18 of 44 row files and 18 of 44 scenario modules are level triplets of just 6 bases — the analysis row triplets differ in 8 of 46 lines, the scenario triplets in 4 of 11. 18 row files name "after_registration_beginner" as a literal back target (21 occurrences) — rows every level walks through, so the beginner target is spelled into the data for all three levels. The module repairs that at runtime, in four places: prefix matching at tutor_session.py:413-415, state-name formatting at :135-138, and the level re-derived at :158-164 and :249.

Solution. Keep one row per state, and make level a parameter of resolution instead of part of the name: row_for(state, level) resolves next / back targets and the item key from the learner's level. 44 rows collapse to 32, the level rule lives once in the module that owns routing, and the 44 fixture dicts become one generated table reached through the seam.

Wins
  • Locality: the level rule in one place, not four
  • Leverage: a new level costs data, not 6 rows + 6 scenario modules
  • 12 rows, 12 scenario modules, 12 fixture dicts (~350 lines) deleted
  • No magic-string surgery inside the module
  • Interface unchanged — callers of TutorSession never see it
Cost: M. Mechanical but high-touch: 12 row modules collapsed into 6, their 12 scenario twins, the table's assembly, and the item-name path in tutor_session.py.
Test first: a traversal of all three level paths through TutorSession.submit, asserting which row each state reaches. The 22 transition tests and 38 machine traversals already exist, so the net is real.
ADR note: ADR-0002 chose one-module-per-state deliberately, and this keeps that — it only removes the level suffix. The 44 fixture dicts move with this candidate: they exist to drive rows from the row's own file, so they are only deletable once the row becomes a function of (state, level).

2 · Make the Summary answer the status question

Strong fixes a live bug
The deep module returns a bag of 17 numbers, so the templates derive task status themselves — and they disagree, live, on the same learner state.

Problem. Summary (session.py:68-98) has 17 flat fields: 12 are read by templates, 2 by views.py (phase, session_id), and 4 — status_badge, current_step, roleplay_progress, completed_modes — are consumed only by tests. The two task lists show the cost of a shallow view: main_menu.html:167-171 asks key in completed_option_values and renders Completed / Not Started; menu.html:34-37 asks the same, then adds a positional fallback — forloop.counter <= analysis_progress.completed — that stamps ✅ Completed on tasks the learner has not opened. With one analysis task in progress the sidebar says task 2 ✅ Completed and the main menu says ⬜ Not Started, for the same session. The status vocabulary lives in 11 templates, not in the module.

Solution. Deepen the view: progress() returns sections of rows that already carry their state — sections: [{title, rows: [{key, label, status}], completed, total, percentage}] with status ∈ not_started | in_progress | completed, plus finished / started. The slug rule at tutor_session.py:158-164 stays behind the seam. Interface 17 fields → ~8, and the templates stop computing anything.

Wins
  • Locality: status in the module, not in two templates
  • Leverage: one rule, every page agrees by construction
  • The live sidebar contradiction disappears with it
  • 4 test-only fields and the positional fallback deleted
Cost: M. The Summary's producers/consumers: tutor_session.py:198-294, menu.html, main_menu.html, export.html, views.py.
Test first: one badge per task in both pages, driven through TutorSession with analysis_task_1 = in_progress — red today, green after.
ADR note: ADR-0001 forbids the view reaching past the module into session state — the Summary shipping raw option values (completed_option_values) is that leak surviving into the new interface. Deepening the view closes it. The module already branches on state at :243-255, so the vocabulary is there; it is the returned shape that is shallow.

3 · One seam for the option protocol

Strong
An option is one concept, but its label comes from three places that merge into a flat dict — and its rejection copy is written in the view, not the row that defines the rejection.

Problem. _make_turn flattens three label sources into one value→label dict: scenario options, the row's nav map, and back / retry synthesised by _navigation_options (tutor_session.py:515-548). Its own docstring states the tie-break — "scenario-defined options win on clashes" (:535) — so a row's nav label silently loses; 4931690 "align role menu labels with canonical routing" (3 files, +35/−11) is one such realignment. The origin of an option is then gone: the template gets a flat dict (chat.html:36-42) and cannot tell a nav affordance from a role choice, so .system-options / .system-btn in style.css:439-462 has no consumer at all. Rejection is worse: every row carries a rejected copy the module drops, and views.py:64-74 infers rejection from the turn count (turns[-1].role == "user" and summary.phase != "finished") with a copy hardcoded in the view at :73. The three sources of "revise is possible here" — the scenario's options, the row's accept, the row's next/effects — must be kept in step by hand: 9 scenario modules + 9 row files carry the revise trio, and 2d1e88f paid 10 files for it.

Solution. Give the seam one vocabulary: the module returns options as typed records — {value, label, kind: choice | nav | retry} — and surfaces the row's own rejected copy as a field on the turn. The template styles by kind, the view renders the rejection the row wrote, and a clash between a nav label and a choice label becomes a construction the table can state instead of a merge order.

Wins
  • Depth: the merge rule is the module's, not the template's
  • Locality: rejection copy lives with the row that rejects
  • The shadowing class of label bugs becomes unrepresentable
  • .system-options CSS gets a real consumer, or goes
Cost: S–M. _make_turn / _navigation_options, chat.html, views.py, the option assertions in test_tutor_session.py and test_views.py.
Test first: assert the current turn's options carry kind, and that a rejected input surfaces the row's rejected text through TutorSession — both red today.

4 · Assemble the registries from the modules that exist

Worth exploring
Two hand-maintained mirrors of 44 modules each: 257 lines whose only job is to say the same thing the package already knows.

Problem. tutor/scenarios/__init__.py (132 lines) and tutor/transitions/__init__.py (125 lines) import every module and restate it as a dict entry — 44 + 44 pairs. SCENARIO["states"] is append history: analysis_task_2 sits between data_collection and roleplay_idea, so the flow order is a side effect of the order someone pasted the entries. A module that exists but is not registered is invisible: the graph checks in _validate.py only see registered rows, so an orphan state module cannot fail validation.

Solution. Derive the maps from the package — walk tutor/scenarios and tutor/transitions, take each module's declared STATE / row, and keep one small STATE_ORDER list as the flow declaration (the one thing the filesystem cannot state). Registration stops being a thing a contributor can forget, and the validation sweep can cover modules that forgot to register.

Wins
  • Depth: the package is the registry
  • Locality: flow order declared in one list
  • ~250 lines of mirror deleted
  • Unregistered modules become a validation failure
Cost: M, and it has a sharp edge.
Spike first: a package walk inside Django app loading. The import cycle is already worked around by two deferred imports (tutor_session.py:88, 91); a filesystem walk must not re-open it. Half a day, throwaway.

5 · Put "has this learner started?" in the interface

Worth exploring
A fact every caller needs is only available by catching an exception — so the callers spell the probe themselves, twice without a catch.

Problem. progress() raises RuntimeError("Session not started") (tutor_session.py:198-201). views.py:21-31 translates that into None — "the single place that translates that into None so the views never spell the 'is it started?' probe themselves" — and three sites honour it (:42, :95, :139), but :61 (chat) and :122 call session.progress() bare. The template proxy is a third spelling: summary.user_name is None as a start test (main_menu.html:143-145, 176-181). "Not started yet" is a real state of a language lesson, so it travels as a crash.

Solution. Let the interface answer the question: started() / finished() booleans, and progress() that returns a zero-state Summary for an untouched session instead of raising. The view helper, the bare calls and the user_name proxy all collapse into one call.

What I'd build first

Candidate 2 — the Summary that answers the status question. It is the only candidate that removes a bug a learner can see (the sidebar stamping ✅ Completed on a task they never opened, menu.html:36-37), it deletes 4 test-only fields and 2 template derivations, and it makes the ADR-0001 seam deeper rather than wider: status vocabulary behind progress(), templates that render what they are told.

Then candidate 1 — the axis parameters. It is the structural win: 12 rows, 12 scenario modules and their 12 fixture dicts deleted, and the level rule in one place. It deserves its own session because it is wide, mechanical, and ADR-0002 adjacent.

Run each as /tdd against the red test named on its card. Use the /codebase-design vocabulary in the grilling: the seam that changes here is the Summary's shape and the row's resolution, not the interface of TutorSession.

What I'd leave alone

  • TutorSession's five verbs — start · submit · back · progress · turns is a genuinely deep module (548 lines behind a call surface you can drive end to end), and ADR-0001's cutover is complete at the view layer.
  • The Storage and Feedback seams — two adapters each, tests run on MemoryStorage with no Django, the LLM behind one function. This is the shape the other candidates are reaching for.
  • ADR-0002's one-module-per-state — the cost above is the level suffix, not the module count.
  • The graph checks in tutor/transitions/_validate.py — reachability, back symmetry, nav coverage. They are the reason the table is trustworthy at 44 rows.
  • chat.html is data-driven (option loop, message list, inline JS filling the input) — the presentation problem is the protocol above it, not the template itself.
